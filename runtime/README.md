# Validation runtime

`golf setup` builds the embedded Docker context. Setup needs network access. Fixture setup, reference audits, and checks use only the locally cached image and never pull automatically. Interactive practice uses the player’s native tools and dotfiles. The base image digest, jj 0.44.0 binary checksums for Linux arm64/amd64, and selected security-fix package versions are pinned. Other Debian package versions resolve when building; `/usr/local/share/golf-packages.txt` records the installed versions. Every attempt records and reuses the resolved image ID, so rebuilding the tag cannot silently change an existing attempt's checker environment. Preserve that image when resuming or retrying saved attempts.

Fixture setup, reference audits, and checks run as UID/GID 1000:1000 with a read-only base filesystem, no network, no Linux capabilities, and no privilege escalation. Each attempt owns one labeled Docker volume mounted at `/workspace`. No host directories, credentials, agents, or Docker sockets are mounted. The disposable home and temporary files live under a 64 MiB `/tmp` mount. CPU is capped at one core, memory and total memory plus swap at 512 MiB, processes at 128, open files at 256, and each file at 16 MiB. Interactive sessions stop after one hour; scripted submissions and individual validation commands stop after ten seconds. The Docker default seccomp policy remains enabled.

Setup containers are removed before native practice starts. The native working directory persists under the application state directory. Returning from the native tool checks those files using the Docker validators. Native practice has normal host permissions and shell process behavior. Restart recovery removes containers only for the application's recorded attempts. Retry uses another volume. Deleting an attempt workspace requires an owner label matching the attempt ID.

Validation cleans up any legacy interactive containers first. File snapshots are decoded in memory, without extracting to host paths. Snapshots reject traversal, duplicate paths, links, devices, and FIFOs. They allow at most 4096 entries, 2 MiB per file, and 16 MiB total file data. Captured stdout and stderr each stop at 2 MiB. Stdout exercises replay the submitted file in a fresh workspace for every fixture. Repository queries run against independent copied snapshots inside new containers.

Docker volumes have no portable aggregate disk quota. A command can create many individually bounded files until its execution deadline. Snapshot limits prevent loading those files into application memory but do not retroactively prevent disk consumption. Use curated exercises and a Docker VM with a configured disk limit. The embedded TUI pane parses child output through a terminal emulator and drops OSC 52 clipboard writes. Full-terminal handoff (`golf --classic` or `golf play`) instead sends child output directly to your terminal. Captured output displayed by the outer application is sanitized. Containers are an execution boundary, not a guarantee against kernel or runtime vulnerabilities, and local scores provide no adversarial integrity.

From the repository root, run `just setup` followed by `just integration` to exercise the runtime on the current Docker host. Integration is split into six shards so each Go invocation has a 20-minute deadline; `just integration ancillary` selects one shard. Run `just audit-solutions` separately for starter/reference audits and `just smoke` for host terminal handoff. These checks use uniquely labeled test containers and volumes. See [CONTRIBUTING.md](../CONTRIBUTING.md#checks) for prerequisites and image overrides.

`golf doctor` checks daemon access and image presence only. It does not start a test container, verify native practice tools, or establish that integration or reference audits pass.
